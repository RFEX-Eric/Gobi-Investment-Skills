# 下一轮优先做什么

2026-10-16 维护建议。下面区分已做的局部改进与仍待开发、验证的方案，**不代表这些方案都已上线**。本轮四行业原始实测使用旧交付策略，是问题基线；新策略和上下文装配不能借用这四份报告作为质量通过证明。上线版本以产品手册和更新记录为准。

## 1. 先让关键事实完整进入报告

本轮已在代码中调整公开发现上下文：保留全部步骤的紧凑覆盖审计，优先按步骤轮流纳入完整证据，再放公司线索和长摘要；仍限制 24,000 字符，明确记录传入与遗漏数量。相同合成夹具中长摘要场景从 1/30 条变为 10/30 条，说明摘要挤占问题得到缓解，不能说明真实报告已掌握更多事实或写得更好。

下一轮要按“来源 → 证据 → 行业认知 → 正文 → 首页”逐段检查：一个关键数字在哪里丢失了，条件在哪里被简化了。对证据的选择应结合本次研究问题、技术路线和事实用途；完整段落过长时取相关段落及其必要上下文，不只取文章开头。没有选入的材料继续保留并明确计数，不将所有未选内容写成“未知”。

验收应使用固定材料与固定框架对照，核查同一组事实在各阶段的保留情况，同时检查是否引入了新错误。增加事实数量不是唯一目标；错误的单位、测试对象或版本会比少一项数字更有害。

## 2. 为决定性原文安排真正的阅读步骤

新策略已经要求在原有工具预算内减少重复泛搜、优先读取已有原始链接。这仍是指令，**尚不是有单独输入、结果和验收条件的原文阅读阶段**。

下一轮可在发现候选后，先选少量决定性产品页、论文或报告，明确要回答的问题和要找的字段，再执行有上限的读取。优先读取原文已有小节或页码；访问失败则交接缺口，不重复搜索直到预算耗尽。增加步骤前先确定总费用、停止条件和预算分配，不默认在现有调用之外无限追加。

公众号、小红书先选少量已知相关文章测试用户授权的获取路径，逐项核对标题、作者、日期、原文地址和实际取得的正文，再决定是否扩大接入。公开搜索命中、摘要、转载、正文和用户提供材料分别标记。平台取得的网页正文、模型摘录和打开动作也要分开：它们不能互相替代，更不能自动升级为“全文已读”。

## 3. 给每项事实保留条件、版本和精确位置

本轮增加的公开知识候选把有来源的模型主张与短引文分开保存，继续等待团队复核；它并不等于完成了下面的结构化证据库。当前日期字段只接受完整日期，只有年月的资料需在主张或限制中原样保留，不能补造具体日。

下一轮一条事实至少应能回答：

| 字段 | 要解决的问题 |
| --- | --- |
| 主张与证据身份 | 说的是什么，是厂商规格、作者实验、第三方估计，还是分析推断？ |
| 对象、条件与版本 | 对哪个产品／型号或论文版本成立？数值、单位、指标原名及测试设置是什么？ |
| 来源与精确位置 | 原始 URL、资料版本、已有页码／小节／段落在哪里？没有定位就明确未知。 |
| 日期与读取范围 | 发布日期精度是什么？取得的是正文片段、摘要还是受限页面？ |
| 使用与更正记录 | 哪份报告、哪项判断引用过？谁做了纠正，后续版本怎样变化？ |

编号和版本要让同事能从首页判断追到事实，再追到当时实际使用的来源。网页变化时新增版本，不覆盖旧报告当时的证据。事实之间有冲突时并列保存，不能通过覆盖旧值消除分歧。涉及项目内部资料的事实仍留在项目授权范围内。

长期积累还需跨研究去重：相同来源与相同主张复用证据，新增一次使用记录；新的数值、条件或纠正单独留版本。当前按单次研究限制候选数，尚不能代替长期知识库的去重、过期检查与容量管理。

## 4. 在交付前加入明确的质量检查

下一轮将“生成完成”与“适合交给投资人阅读”分开。先做可机械验证的检查：图表是否有效、来源编号是否能定位、首页数字是否带对象和单位、正文引用能否回到本次证据、已知限制是否保留。市场规模还应检查年份、区域、范围、假设和计算是否一致。

专业质量需要人工验收：一分钟是否看懂首页，概念和路线是否解释清楚，公司为什么可比，技术差异怎样影响用途或商业机会，关键观点是否超出证据。不能仅凭图表数量、公司数量或模型自评分宣布通过。

检查未通过时保留报告草稿、完整来源及具体问题，显示“待复核”或“需补充”，不删除旧结果，也不自动反复付费重跑。团队的纠正可以形成带适用行业和版本的规则，再用同类任务复测；评分规则变更仍需团队确认。

## 5. 把后台连续运行单独验收

现有任务在云端保存，但按小时接续会放大多阶段研究的等待。本轮已经补充实际接续入口调用时间记录，以及管理员对失败任务已有响应的用量核查。前者不能区分手动与定时触发，也不能证明完整研究成功；后者不自动重发请求。

下一轮应验证更及时、可观察的服务端触发，区分临时预算排队、额度确实不足和结果不明的费用预留。验收要在关闭研究页面后观察完整任务完成，不能用“设置已启用”代替运行证据。继续保留预算、并发和停止原因，不自动重发提交结果不明的请求。

## 6. 三个值得从 N.E.I. 方法发展为产品功能的方向

| 优先级 | 具体功能 | 平台怎样实现 | 手测标准 |
| --- | --- | --- | --- |
| 1 | 可复算的市场规模卡 | 保存范围、年份、单位、需求数量、采用率、单价及每个假设的出处；代码计算低／基准／高情景，报告引用该版本 | 改一个假设可重算；无法支持的输入保持未知；不将假设显示为事实 |
| 2 | 核心判断的证据讨论卡 | 一个判断对应支持证据、反对证据、尚未解决的问题和团队结论；评论指向具体资料版本 | 同事能从首页观点回到依据，看到分歧如何处理，修改后保留前版 |
| 3 | 按应用场景调整研究重点 | 同一行业内分别判断应用成熟程度，再选择验证问题；成熟度与公司融资轮次分开记录 | 初创公司不会自动被当作早期产业；同一行业不同应用可以有不同重点 |

第一个方向参考 N.E.I. 的[市场规模测算方法](https://nei-pevc.com/posts/70)，将计算逻辑做成可复核结构，而非只生成一个市场数字。第二个方向借鉴其[多视角与矛盾梳理](https://nei-pevc.com/posts/43)思路；模型自评不算独立核验。第三个方向参考[产业生命周期方法](https://nei-pevc.com/posts/67)与[端到端工作流](https://nei-pevc.com/posts/98)，具体分类仍需团队按行业校准。

不会直接采用外部模板里的统一市场门槛、未经核实的提升百分比或自动评分结论。这些页面是方法参考，页面自述的质量评分不构成本平台验证。

先完成以上质量对照，再扩大自动生成规模，扩展 biotech、healthcare 等方向时请对应领域同事校准专业框架。长期记忆仍按既有分层：公开知识和检索方法可团队复用，内部项目材料默认只在原项目；明确授权导入的团队历史报告按团队权限复用，不进入公开查询。
